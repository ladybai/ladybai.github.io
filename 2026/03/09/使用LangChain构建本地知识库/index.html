使用LangChain构建本地知识库

//

基于LangChain框架搭建一个本地智能问答系统

目前最主流的方案是RAG（Retrieval-Augmented Generation，检索增强生成）

一、 系统架构设计

一个标准的 RAG 智能文档问答系统包含以下 5 个核心模块：

  1. 文档加载 (Document Loading)： 根据不同的文件后缀（.pdf, .docx, .txt），使用对应的 Loader 将文档内容读取为纯文本格式。
  2. 文本切分 (Text Splitting)： 因为 LLM 有上下文长度限制，需要将长文档切分成合适大小的“文本块 (Chunks)”。
  3. 向量化 (Embedding)： 使用 Embedding 模型（如 OpenAI、HuggingFace 或 Bge 模型）将文本块转换为数学向量。这里选择openAI的text-embedding-3-small模型
  4. 向量数据库 (Vector Store)： 将转换后的向量存储起来（如 FAISS, Chroma,Qdrant），以便快速进行相似度检索。这里为了方便，选择Qdrant的本地内存形式的向量存储
  5. 大模型问答 (LLM Generation)： 用户提出问题后，系统在向量数据库中检索出最相关的文本块，将其作为“背景知识”连同用户问题一起提交给大语言模型（LLM），由大模型生成最终的准确答案。

2、文本切割：

需要将我们的文本进行切割，切割成更小的块，以便于嵌入（Embedding）和向量存储

这里需要注意切割的粒度，粒度直接决定了向量数据库的检索质量。如果切的太粗，语义会模糊，如果切的太细，会丢失上下文。

比如上面相同的文档，chunk_size = 500时，切割结果为49个块；当chunk_size=1000时，切割结果为37个文本块。

  • 当切割的太细，比如chunk_size<100, 像是在看碎纸机，模型很难知道“它”指代的是什么；

  • 当切割的太粗（比如chunk_size>1000),一句话包含太多关键词，向量化后会稀释掉关键特征，导致搜索不准；

通常建议chunk_size设置为300-800之间，但是要具体场景具体分析。

chunk_overlap：为了防止重要信息刚好被切在两个块的交界处。一般设置为chunk_size的10%-20%。

​

上面两个问题的区别：问题1是个综合问题，文中的场景比较多，属于比较复杂的问题，这个时候如果粒度过细，则总结能力会减弱；问题2属于细节问题，这个在文中是一句话中的细节，如果粒度过粗，则可能会忽略到文本块中的细节。

总结后我们得到哪些场景适合细粒度，哪些场景适合粗粒度：

你可以根据原始文件的性质来决定：

  1. 法律条文/规章制度：建议较细粒度。每一条规则都是独立的，混合在一起会干扰检索。
  2. 小说/传记/叙事散文：建议中等粒度 + 较高重叠度。需要维持故事情节的连续性。
